# Universal Web Extraction + QA — Research Findings & Architecture Recommendation

**Date:** 2026-08-31
**Run:** `wf_f445f586-e86` — 101 agents, 19 sources fetched, 95 claims extracted, 25 verified, 4.2M subagent tokens, ~53 min
**Scope set by:** general-purpose (all site types) · framework/tooling survey · open-source-project-first, monetization deferred

## 0. How to read this document

Findings come in **two tiers**. The distinction is not cosmetic — in the tier that *was* audited, 6 of 25 claims died, including three that looked airtight.

| Tier | Meaning | Trust |
|---|---|---|
| **[V]** Verified | Survived 3-vote adversarial verification | Cite directly |
| **[U]** Unverified | Extracted by one agent from one source, never audited — the verification budget ran out | Treat as a lead, re-check before it drives a decision |

## 1. Headline

**The unoccupied gap is live-page structured extraction, and the strongest evidence for it is a negative result: no small open extractor publishes reproducible numbers on any public web-extraction benchmark.** Every vendor in the survey — NuExtract, Schematron — reports only private internal sets. Combined with a measured 38-point human gap on live pages, that is the contribution nobody has made.

Layer by layer, the build-vs-buy call is unusually clear:

| Layer | Call | Why |
|---|---|---|
| Crawl / render | **Consume** | Crawl4AI, Apache-2.0, actively maintained. Not a differentiator. |
| Hydration payloads | **Consume + extend** | `njsparser` exists; RSC flight data needs a second parser. |
| PDF / documents | **Consume + report** | Commoditised, crowded leaderboard, specialists beat frontier models. |
| **Live-page structured extraction** | **BUILD** | 48.58% vs 86.60% human. The gap. |
| Retrieval / QA | **Consume + route** | Graph wins only on multi-hop, at 40–57× indexing cost. The *router* is the deliverable. |
| Temporal storage | **Consume, constrained** | Options narrowed sharply — see §5. |
| Public benchmark | **BUILD** | The moat, the dev harness, and the distribution channel. |

## 2. Crawl and render layer

**[V] Crawl4AI is Apache-2.0 *plus a mandatory attribution addendum*.** The LICENSE is 68 lines: 1–51 are verbatim Apache 2.0 ending at "END OF TERMS AND CONDITIONS"; 54–68 add an Attribution Requirement that a credit line be "displayed in a prominent and easily accessible location" — NOTICE, README, About, Credits, or CLI help. GitHub's detector reports plain `Apache-2.0` because it ignores post-terms addenda. This is a **notice obligation, not copyleft**, so it remains consumable. Downstream docs must say *required*, not *recommended* — the README contains both phrasings on adjacent lines (L1126 vs L1129) and L1129 is the operative one.

**[V] It is a Playwright orchestration wrapper, not an independent engine.** Adopting it inherits Playwright's footprint. A CDP-attach path (`use_managed_browser` + `cdp_url`, `browser_mode="docker"`) softens the local-binary requirement.

**[V] It ships block *detection*, not bypass.** v0.8.5 (18 Mar 2026) added a three-tier classifier — Tier 1 named vendors (Cloudflare, Akamai, DataDome, PerimeterX), Tier 2 generic indicators on small pages, Tier 3 structural integrity — wired to `CrawlerRunConfig(max_retries, proxy_config, fallback_fetch_function)`.
> **The sibling claim that a consumer therefore needs no stealth/proxy layer was REFUTED 0–3.** Budget for building your own.

**[V] `flatten_shadow_dom` (v0.8.5+) force-opens closed shadow roots** — a real answer for Web Components (Lit, Stencil, Shoelace, Angular Elements). It is **orthogonal** to hydration-payload extraction.

**[V] Maintenance supports dependency viability:** nine PyPI releases in seven months (0.8.0 Jan 16 2026 → 0.9.2 Jul 15 2026). Not a security vetting — **CVE-2026-57571 (arbitrary file write)** was reported ~Jun 2026, fixed in 0.9.0.

**[V] Firecrawl's core is AGPL-3.0** (SDKs/UI MIT) and genuinely self-hostable, but the self-hosted stack is materially weaker: **Fire-Engine (the anti-bot/stealth-proxy layer) is not included**, and agent/browser/interact, screenshots, page actions and specialised media formats route to Firecrawl Cloud. The shipped Compose is explicitly disclaimed as "a source-aligned starting point, not a production architecture," with authentication disabled by default.

**[V, medium] Firecrawl already occupies the "universal crawl+render+extract" category** — but largely as a *cloud* claim. The AGPL repo alone is not a ready-made universal dependency.

**[U] Firecrawl's vendor numbers** — 96% web coverage, P95 scrape latency 3.4s — are vendor-published with no stated methodology and apply to the hosted service.

> ⚠️ **No third-party measurement of throughput, memory footprint, anti-bot precision/recall, or production adoption exists anywhere in this evidence set.** Everything above is first-party vendor documentation. Appropriate for license and feature-existence claims; not for performance.

## 3. Structured extraction — the layer worth building

**[V] There is no near-solved SOTA for schema-constrained extraction against LIVE pages.** On LiveWeb-IE (Mar 2026), the best system across all method×backbone cells reaches **48.58% overall F1** (VGS + GPT-4o), versus 26.76% for the strongest baseline (AutoScraper + GPT-4o) and **86.60% for human evaluators** — a 38.02-point gap the paper states itself.

> ⚠️ **This is a GPT-4o-era result.** No GPT-5.x, Gemini 3, or Claude Opus 5 backbone was evaluated. It must never be phrased as an Aug-2026 frontier ceiling.

**[V] Static-snapshot benchmark scores (SWDE/WebSRC family) should be discounted when choosing a production stack** — they demonstrably fail to transfer to live, temporally evolving sites. This is the authors' own conclusion, not a downstream inference.

**[V] SWDE headline numbers are not comparable across 2026 papers, and no open small model demonstrably holds SWDE SOTA.** AXE's 88.1% F1 (0.6B) is an unreviewed preprint comparing **k=0 page-level F1 against k=1 encoder baselines** (WebLM_LARGE 87.57, MarkupLM_LARGE 85.71) — a 0.53-point margin under a protocol mismatch. Co-Scraper's fine-tuned Qwen3-8B at 94.78% Non-Univ. F1 sits **below** the Gemini-3.5-Flash baseline the same paper reports at 95.23%.

**[V] Field-level metrics overstate usable page quality by ~3×.** Co-Scraper: 94.78% end-to-end F1, 90.39% field-level correctness, but only **70.73% page-level success** — ~29.3% of pages carry at least one imperfect field. **Page-level success is the number that matters for an unattended pipeline.**
> Caveat: 70.73% is Co-Scraper-specific, not a class ceiling — Gemini-3.5-Flash reaches 77.86 in the same table.

**[V] Query-aware DOM pruning is the highest-leverage cheap stage.** It cuts SWDE page context **~96.5% (19.7K → 0.7K tokens)** without collapsing extraction quality, independently corroborated at **97.9% (16,581 → 350.6 tokens)** by a different 2026 group using a 0.6B pruner.
> Caveat: measured from an already-cleaned baseline on static 2011-era SWDE HTML. Do not assume transfer to hydrated SPAs or canvas pages.

**[V, medium] Induced selectors decay measurably** — LLM wrapper-generation methods lose **>15 absolute F1 points** on structurally evolved versions of the same sites.
> Caveat: measured across a ~14-year snapshot gap on n=100 pages. It is **not a drift rate** and cannot be annualised. The engineering implication — that a selector cache needs automated drift detection and repair, not one-shot induction — is a reasonable inference but is *not* tested by the paper.

**[V] Small open extractors are license-fragmented and benchmark-opaque.** NuExtract-2.0-8B is MIT (from Qwen2.5-VL-7B-Instruct), 2.0-2B is MIT (deliberately built on older Qwen2-VL-2B to stay commercially usable), but **2.0-4B carries the non-commercial Qwen Research License**. The family publishes **no** SWDE, WebSRC or any public web-extraction result — only a vendor bar-chart over a private ~1,000-example set.
> Superseded: **NuExtract3 (Apache-2.0, ~4B)** now exists. Any 2.0-8B recommendation dated today is a worse license/size choice.

**[U] Schematron V2 is closed-weights, hosted-only.** Only Schematron 3B/8B (V1) are open on HuggingFace. By the vendor's own numbers the open **V1 8B beats both V2 models** (SimpleQA 85.58 vs 83.10 / 79.42). V2 trades accuracy for throughput: 4.14 req/s on a single H100 vs 1.63 for V1-8B, at $0.06/$0.15 per 1M in/out tokens. No standard benchmark results published.

## 4. Retrieval and QA — consume and route, do not innovate

Every recovered claim points the same way: **the graph is a routed special case, not a substrate.**

**[U] The sign of the GraphRAG-vs-chunk gap flips with query class.** GraphRAG-Bench, Novel dataset: Basic RAG (w/ rerank) **60.92** on Fact Retrieval vs MS-GraphRAG **49.29**; on Complex Reasoning Basic RAG drops to **42.93** while MS-GraphRAG rises to **50.93** and HippoRAG2 reaches **53.38**.

**[U] Framework choice is domain-sensitive and can fail catastrophically.** Medical dataset: MS-GraphRAG **38.63** vs Basic RAG **64.73** — a ~26-point deficit — while HippoRAG2 scores 66.28 and LightRAG 63.32.

**[U] Retrieval token cost differs by an order of magnitude between graph frameworks:** MS-GraphRAG (global) ~4×10⁴ tokens/query, LightRAG ~10⁴, **HippoRAG2 ~10³ — roughly 40× cheaper than community-summarization GraphRAG at comparable or better accuracy.**

**[U] Prompt inflation actively degrades quality**, not just cost: context expands 7,800 → 40,000 tokens as difficulty rises, introducing redundancy that hurts context relevance.

**[U] Independent unified-protocol evaluation agrees, and the gains are small.** HotpotQA F1 (Llama-3.1-8B): RAG 60.04 vs HippoRAG2 63.01, Community-GraphRAG Local 61.66. MultiHop-RAG accuracy: RAG 67.02 vs HippoRAG2 70.27. **Pure-triplet KG-GraphRAG is far worse than plain RAG** (42.60 F1 / 41.24 acc).

**[U] Graph construction costs 40–57× plain chunk RAG in indexing wall-clock.** MultiHop-RAG: 135s (RAG) vs 5,560s (Community-GraphRAG) vs 7,702s (KG-GraphRAG). KG-GraphRAG retrieval also ~8× slower (14,434s vs 1,724s). Storage is comparable (117–165MB).

**[U] The dominant graph failure mode is lossy indexing:** only **~65.8%** of answer entities appear in the constructed KG on HotpotQA (65.5% on NQ) — about a third of answers unrecoverable regardless of retrieval quality.
> 🔁 **This is the same claim as PRD v2 §0 finding #9, same paper.** Not new evidence — a *convergence* between the old PRDs and this pass, and one of the few places they agree.

**[U] Community-summary mode collapses on small open models:** NovelQA 17.48% (Qwen2.5-7B) / 10.93% (Llama) versus 43.34% / 43.64% for GraphRAG-Local. Attributed to semantic noise from aggregation plus the model failing to emit required JSON.

**[U] Eager graph construction is hard to justify:** GraphRAG-style full indexing ~$48 of GPT-4o inference for a moderate corpus; **LazyGraphRAG defers extraction to query time for ~0.1% of that (~1000×)**. E2GraphRAG separately reports GraphRAG-Local at 13,793s (~4h) to index one ~200k-token book vs 1,397s (9.9×).

**[U] The LLM-per-chunk extraction step is substitutable:** replacing it with classical SpaCy NER for the entity graph — reserving the LLM for a hierarchical summary tree — is what produces the ~10× indexing speedup.

**[U] Graph pipelines on 7–8B models are operationally brittle:** authors needed retry loops for both LightRAG and GraphRAG, and could not run FastGraphRAG at all against local 7–8B models even with five retries per call. Direct support for making **constrained decoding a hard requirement, not an optimization**.

**[U] Published GraphRAG win rates are inflated by LLM-judge position bias** — one popular method's 66.7% win rate fell to ~39% after bias correction. Swapping presentation order can flip a verdict. Microsoft's own 72–83% comprehensiveness figures are vendor-published. **A new eval harness must control for order.**

> ⚠️ **Do not double-count.** The VentureBeat article (2026-08-02) reporting 60.9/60.1, 53.4/42.9, 64.4/51.3 *cites GraphRAG-Bench* — the same source as the Novel-dataset numbers above, and a different dataset slice. These are one body of evidence, not two.

## 5. Storage and temporality — options narrowed hard

**[U] KuzuDB was abandoned by its vendor in early October 2025.** Repo archived ("working on something new"), docs moved off the company site. Final vendor release **0.11.0, July 2025** — no first-party release in over a year. MIT, so forking is legally unobstructed; a community continuation exists (**Kineviz's "bighorn"**) but is nascent, single-company-led, and actively soliciting co-maintainers.
> Note the meta-lesson: commit count, release cadence and project age were *misleading* health signals here. VC-backed single-vendor OSS carries abandonment risk those metrics do not capture.

**[U] Graphiti itself now deprecates Kuzu** (README, 2026-08-26) on unmaintained-upstream grounds and directs new projects to Neo4j or FalkorDB.

**[U] Graphiti has no Postgres/pgvector or DuckDB backend.** Supported: Neo4j 5.26+, FalkorDB 1.1.2+, Amazon Neptune paired with OpenSearch Serverless. **This prices PRD v2's open decision #1 — "borrow the bitemporal model into Postgres" means writing a driver**, which the PRDs did not account for.

**[U] Graphiti's OSS core carries no performance guarantee.** Zep's own comparison table concedes all quoted latency figures (sub-200ms at scale) belong to the closed-source Zep "Context Graph Engine." Repo health (2026-08-31): Apache-2.0, 30,450 stars, 3,090 forks, 487 open issues, v0.29.3 (2026-07-27), last push 2026-08-30 — actively maintained. Ingestion is LLM-bound, needs reliable structured output (small/local models cause failures), and ships **default concurrency of 10**, bounding bulk throughput.

**[U] Graphiti's documented model is a per-fact validity window with invalidate-don't-delete**, supporting point-in-time queries and episode-level provenance. The README does **not** enumerate the "four-timestamp model" the PRDs attribute to it — source that from arXiv:2501.13956 or the code, not the README.

## 6. Hard modalities

### Hydration payloads — the biggest cheap win, and nearly unexamined

**[U] Next.js exposes server-rendered data in two distinct formats:** the legacy `__NEXT_DATA__` JSON script tag (directly parseable from raw HTML, no JS execution), and, on RSC sites, **flight data serialized into `self.__next_f.push()` calls** — chunked in a React-specific wire format where naive JSON parsing fails. A universal extractor needs **two parsers for Next.js alone**.

**[U] `njsparser` (github.com/novitae/njsparser) already parses flight data** — `BeautifulFD()` with `find_iter()` chunk iteration, plus a CLI that detects which format a site uses and lists page routes. Candidate off-the-shelf component.

**[U] Hydration payloads cover only the first page of paginated content**; subsequent pages load via REST/XHR, so a complete extractor must pair payload parsing with **API interception**.

### PDFs and documents — commoditised, do not rebuild

**[V] OmniDocBench is the benchmark to report on, not replace:** 1,651 real-world PDF pages, 10 document types, 5 layouts, 5 languages, 28 block-level + 4 span-level annotated element types, Apache-2.0, maintained through Jul 2026.

**[V] Small specialized open OCR VLMs outrank frontier general models by a wide margin.** OmniDocBench v1.6: PaddleOCR-VL-1.6 (0.9B) **96.34** overall / 0.0326 text edit distance / 94.76 TableTEDS; MinerU2.5-Pro (1.2B) **95.75**; GLM-OCR (0.9B) **95.22** — versus Gemini 3 Pro 92.91, Gemini 3 Flash 92.62, Qwen3-VL-235B 89.78, GPT-5.2 86.59.
> **Cite the tier ordering, never the 0.59-point winner.** Leaderboard last updated ~Mar/Apr 2026; the #1 holder is likely already superseded. Rows are author-submitted.

**[U] License risk differs materially.** Docling is clean (MIT code / Apache-2.0 weights). **Marker 2 ships Modified OpenRAIL-M — free only below $5M funding/revenue.** MinerU requires a commercial license above 100M MAU or $20M monthly revenue, plus mandatory visible attribution when offered as a service. **Docling and olmOCR (Apache-2.0) are the only unencumbered picks.**

**[U] License cleanliness and accuracy pull in opposite directions.** olmOCR-Bench: Docling 2.116 **50.3**, Marker 2 balanced **76.0**, Surya 2 standalone **83.3** — the permissive, CPU-viable option is ~26 points behind.

**[U] Throughput spans ~14× on identical B200 hardware:** MinerU 3.4 pipeline 0.54 pages/s vs Marker 2 fast 7.4 pages/s — **~21 days versus ~1.6 days per million pages.**

**[U] The recommended production pattern is a two-tier cascade**, not a single parser: run fast mode, escalate only pages failing a quality gate. Directly reusable as the routing design for the document modality.

**[U] Self-reported parser scores sit ~2 points above the public OmniDocBench leaderboard.** Discount any number from a parser's own repo.

### Benchmark infrastructure

**[U] The gap in evaluation is infrastructure, not benchmarks.** HAL's contribution is a standardized harness orchestrating parallel evaluation across hundreds of VMs, cutting weeks to hours. A new project competing on evals needs **a reproducible harness, not just another leaderboard**.

**[U] Budget anchor: ~$40,000** for 21,730 rollouts across 9 models × 9 benchmarks.

**[U] Two findings that should shape the harness:** increasing reasoning effort *reduced* accuracy in the majority of runs; and agent scores are contaminated by shortcut behaviours (agents searching for the benchmark on HuggingFace instead of solving the task). Leaderboard numbers are **upper bounds requiring trace-level audit**.

**[U] HAL published all 2.5B tokens of agent logs** — a template for differentiation: **publish traces, not just scores.**

## 8. Recommended architecture

```
                    ┌─ Stage 0: profile ─────────────────────────┐
                    │  fingerprint stack · content census        │  [gap: unevidenced]
                    └────────────────┬───────────────────────────┘
                                     ▼
  Crawl4AI (Apache-2.0 + attribution)  ──► YOUR stealth/proxy layer (must build)
                                     │
                                     ▼
                   ┌── FAST PATH ────────────────────────┐
                   │  hydration payload?                 │
                   │   __NEXT_DATA__ → direct JSON       │  ~free, highest ROI
                   │   RSC flight   → njsparser          │
                   │   CMS/commerce JSON API             │
                   │   + XHR interception (pagination)   │
                   └────────────┬────────────────────────┘
                                │ miss
                                ▼
              Query-aware DOM pruning  (~96.5% context reduction)
                                │
                                ▼
              Selector cache — replay if valid          [gate: no LLM]
                   │ stale/absent          │ validate every replay
                   ▼                       │ (drift detection, not one-shot)
              LLM induction → emit XPaths ─┘
                                │
                                ▼
              Constrained-decoding extraction  ← BACKEND UNDECIDED (§9)
                                │
                                ▼
              Entity resolution: source-scoped nodes + SAME_AS canonical layer
                                │
                                ▼
              Bitemporal store (validity window, invalidate-don't-delete)
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
          Chunk retrieval            Graph traversal
             (default)              (multi-hop only)
                    └───────► ROUTER ◄──────┘
                          (the deliverable)
```

**Three principles the evidence forces:**

1. **Cheapest correct extractor first.** Hydration payload → pruned DOM + cached selector → LLM. Each fallback is an order of magnitude more expensive than the last.
2. **Route the graph, never default to it.** Chunk RAG is the substrate; the graph is invoked for multi-hop. HippoRAG2-class retrieval over community-summarization GraphRAG (~40× cheaper per query, better accuracy).
3. **Page-level success is the metric.** Field-level F1 overstates by ~3×.

## 9. Phased plan

| Phase | Deliverable | Gate |
|---|---|---|
| **P0** | **Public benchmark first.** Cross-site-type (static, SSR, SPA, commerce, docs, news), live *and* snapshotted pages. Page-level success as headline metric. Publish traces, not just scores. Control for LLM-judge position bias. | Baselines run: Firecrawl extract, Crawl4AI+schema, frontier model on raw HTML. Table published. |
| **P1** | Crawl spine: Crawl4AI + own stealth/proxy layer + hydration fast path (`__NEXT_DATA__`, RSC via njsparser, XHR interception) | % of gold-set facts obtainable with **zero LLM calls**. This number determines the whole cost model. |
| **P2** | **The differentiator.** Query-aware DOM pruning + selector induction with automated drift detection and repair. | Beat the published live-page baseline on your own benchmark. Page-level, not field-level. |
| **P3** | Entity resolution (source-scoped + `SAME_AS` canonical layer) + bitemporal store | Zero phantom diffs on two identical crawls; provenance survives cross-site merge. |
| **P4** | Retrieval router: chunk default, graph on multi-hop | Router beats *either* channel alone on a mixed query set. |
| **P5** | Modality escalation: PDF two-tier cascade (Docling/olmOCR default). Images/charts/video **gated on a modality audit**. | Only if the audit shows meaningful non-text facts. |

**P0 before P1 is not process theatre.** It is simultaneously the dev harness, the credibility claim, and the distribution channel — and it is the one contribution the evidence says is genuinely unoccupied.

## 11. Genuinely open — nothing here is backfillable from this run

1. **Which constrained-decoding backend?** *All* JSONSchemaBench evidence was refuted. Outlines vs XGrammar vs llguidance vs LM Format Enforcer vs vLLM/SGLang is **entirely open**, and whether per-site schema recompilation is a hidden latency cost needs fresh primary measurement. This is the highest-priority unknown — E2GraphRAG's brittleness finding makes constrained decoding a hard requirement, and we don't know which engine to use.
2. **Tech-stack fingerprinting coverage.** No verified claim. The PRDs' Stage 0 routing table rests on nothing measured.
3. **Video / audio pipelines.** No evidence surfaced at all.
4. **Third-party throughput, memory, anti-bot precision/recall for any crawler.** Entirely vendor-self-reported.

A targeted follow-up run would need to prioritise (1) — it blocks P2 — and can defer (3) until the modality audit in P5.
